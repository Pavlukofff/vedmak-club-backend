# План сайта фехтовального клуба (вселенная «Ведьмак»)

## 1. Общая структура сайта

### Публичная часть
- Главная страница (новости, анонсы турниров, атмосферный вводный текст)
- Блог (статьи, посты)
- **Фестивали** — отдельный список мероприятий, с перекрёстными ссылками на посты блога (у фестиваля — ссылка на пост(ы) о нём в блоге, у поста блога — ссылка обратно на фестиваль, если применимо), с возможностью прикреплять фотографии
- Список участников клуба (публичные профили)
- Таблица боёв / рейтинг побед-поражений
- Список убитых монстров (общий «бестиарий охоты» — привязан к боям конкретных пользователей)
- **Бестиарий** — справочник видов монстров (энциклопедия: описание, тип, опасность), отдельно от «кто кого убил»
- **Школы фехтования** — страницы школ (Волк, Кот, Гриффон, Медведь, Змея, Мантикора, Лиса, Россомаха и т.д.) с описанием и параметрами

- **Расписание** тренировок/занятий клуба
- **Кодекс цеха** — правила и устав клуба (загружен вами, см. раздел 4.6)
- Сборы средств (список активных и завершённых, прогресс-бар)
- Магазин (просмотр товаров, покупка за внутриигровую валюту) + **Лавка алхимика** (зелья/масла/отвары — в разработке)
- **Соц-сети клуба** — блок ссылок в подвале/на главной: соц-сети клуба, соц-сети мастеров школ, соц-сети оружейни
- Регистрация / вход

- Профиль: аватар, ник, уровень, опыт, баланс валюты, дата рождения

### Админ-панель
- **Dashboard** — сводка последних событий для быстрого мониторинга (см. отдельный раздел 4.13 ниже)

## 2. Роли пользователей

Роли полностью управляются через **Django admin** — можно создавать произвольные кастомные роли без изменения кода. Из присланного Кодекса цеха видна реальная иерархия клуба, которую имеет смысл завести как роли по умолчанию (дальше можно добавлять любые другие):

| Роль | Смысл (по Кодексу цеха) |
|---|---|
| Гость | Просмотр публичных страниц, не зарегистрирован |
| Участник (Рекрут и выше) | Личный кабинет, участие в боях/заданиях, покупки в магазине |
| Стажёр подмастерья | Помогает следить за общественной экипировкой школы |
| Подмастерье | То же + доступ к судейству тренировочных боёв (опционально) |
| Мастер школы | Отвечает за экипировку и учеников своей школы; может подтверждать убийства монстров, начислять награды, подтверждать заявки на ранг |
| Десница Главы Клуба (ДГК) | Может накладывать взыскания, отстранять от занятий, замещает Главу Клуба |
| Глава Клуба (ГК) | Полная административная ответственность, отменяет взыскания, назначает мастерский состав |
| Админ сайта | Технический полный доступ ко всей админ-панели (не обязательно совпадает с ГК как человеком) |

Важно: роль в реальной жизни клуба (Мастер, ГК, ДГК) и роль на сайте — не всегда одно и то же (например, у Мастера школы может не быть доступа к управлению магазином). Поэтому, как и раньше, закладываем модель **роль + набор прав (permissions)**, а не жёстко прошитый список:

```
Role {
  id
  name (например, «Мастер школы»)
  permissions: [string]   // например: canConfirmKills, canGrantRewards,
                           // canApproveRanks, canManageBlog, canManageBattles,
                           // canManageShop, canManageUsers, canIssuePenalties,
                           // canCancelPenalties, canViewPenalties, ...
}
```

Роль (или несколько ролей) пользователя обязательно отображается на странице профиля — как в публичной версии (например, бейдж «Мастер школы Волка»), так и в личном кабинете.

Роли назначаются вручную через Django admin (не через саморегистрацию).

## 3. Технологический стек (утверждено)

- **Backend:** Django + Django REST Framework (DRF) для API
- **Админ-панель:** штатный **Django admin**, кастомизированный под сущности проекта (пользователи/роли, магазин, зелья/свитки, ранги, бои, турниры, блог, сборы, абонементы, расписание, кодекс цеха) — это закрывает большую часть требований к разделу 1 «Админ-панель» практически без написания отдельного UI. При необходимости более красивого вида — косметическая тема поверх (django-unfold / django-jazzmin), без изменения логики
- **Frontend:** React (Vite) + React Router — выбран вместо Next.js, так как Django уже отдаёт API и SSR/API routes Next.js не нужны. Next.js стоит рассмотреть отдельно только если для публичных страниц (блог, турниры) критична SEO-индексация
- **База данных:** PostgreSQL
- **Хранение аватаров/изображений:** Django `MEDIA_ROOT` на старте, позже — S3-совместимое хранилище при росте нагрузки
- **Аутентификация:** django.contrib.auth (пароли хэшируются PBKDF2 из коробки) + djangorestframework-simplejwt (JWT для SPA-фронтенда). Защита от типовых атак: CSRF (встроено в Django), троттлинг попыток входа через DRF `DEFAULT_THROTTLE_RATES` или django-axes, обязательный HTTPS на проде. Продвинутые меры (2FA и т.п.) не закладываются — по вашим словам, не требуются

Это не единственный вариант, но такой стек хорошо ложится на описанный функционал и его будет легко разворачивать одному-двум разработчикам.

## 4. Детальная проработка: Профиль, регистрация, аватар

Это раздел, с которого начинаем сборку.

### 4.1 Регистрация

Поля формы:
- Логин (уникальный)
- Email (уникальный, для восстановления пароля)
- Пароль + подтверждение (валидация сложности)
- Отображаемое имя (никнейм персонажа, например «Геральт из Ривии»)
- Дата рождения (реальная — для поздравлений; можно скрыть год, показывать только день/месяц публично)
- Согласие с правилами клуба (чекбокс)

Логика:
1. Проверка уникальности логина/email
2. Хэширование пароля
3. Создание записи пользователя с ролью по умолчанию: `Участник`, ранг по умолчанию: `Рекрут`
4. Стартовые значения: уровень = 1, опыт = 0, баланс = стартовое количество монет (настраивается админом), школа = не выбрана
5. Аватар по умолчанию — один из preset-аватаров (например, гербы школ: Волк, Кот, Гриффон, Медведь)
6. Письмо с подтверждением email отправляется, но **регистрация не блокируется** ожиданием подтверждения — пользователь может сразу пользоваться сайтом. Флаг `emailVerified` при этом остаётся `false`, пока пользователь не перейдёт по ссылке из письма.

### 4.2 Выбор аватара

Делаем оба варианта сразу:
- **Пресеты** — галерея тематических аватаров (школы ведьмаков, монстры, персонажи), без модерации, доступны сразу после регистрации без каких-либо условий
- **Загрузка своего изображения** — доступна **только после подтверждения email** (`emailVerified = true`). Пока email не подтверждён, в интерфейсе показывается пресет-галерея, а загрузка своего файла заблокирована с пояснением «подтвердите email, чтобы загрузить свою аватарку»

Это единственное место на сайте, где подтверждение email обязательно — сама регистрация и вход по email-верификации не блокируются (см. открытые вопросы про восстановление пароля). Ограничение служит простым барьером против массовой загрузки произвольного контента с одноразовых/поддельных адресов.

Модерация загруженных аватаров — откладывается: на старте изображение публикуется сразу после загрузки (после подтверждения email), без очереди на проверку. Позже можно добавить: жалобу от других пользователей + ручной сброс аватара нарушителя на дефолтный со стороны админа/мастера — технически это не блокирует запуск, добавляется отдельным шагом.

### 4.3 Структура профиля (модель данных)

```
User {
  id
  username (логин)
  displayName (никнейм, свободный выбор при регистрации — далее менять только через запрос, см. 4.5)
  firstName: string, optional
  lastName: string, optional
  nameVisibility: "hidden" | "public"   // выбирает сам пользователь — показывать ли имя/фамилию в публичном профиле
  email
  emailVerified: bool             // false по умолчанию, требуется true для загрузки своего аватара
  passwordHash
  avatarUrl
  schoolId: FK -> School, optional        // изначально не заполнено
  rankId: FK -> Rank                      // изначально "Рекрут"
  role: guest | member | moderator | admin
  level: int
  experience: int
  balance: int (виртуальная валюта — кроны)
  birthDate: date
  birthDateVisibility: "hidden" | "day_month" | "full"   // выбирает сам пользователь
  createdAt: date
  isActive: bool
}
```

Имя и фамилия — необязательные поля (пользователь может остаться только под ником, если не хочет раскрывать реальные данные). Видимость в публичном профиле (`nameVisibility`) — выбор самого пользователя, аналогично видимости даты рождения; по умолчанию `hidden`, даже если поля заполнены.

### 4.4 Страница профиля (публичная версия)

Показывает:
- Аватар, ник, школа (или «без школы», если не назначена)
- **Имя и Фамилия** — только если пользователь включил видимость (`nameVisibility = public`)
- Ранг цеха (бейдж/иконка, например «🛡 Рекрут цеха»)
- Роль(и), если есть (например, «Мастер школы Волка»)
- Уровень + прогресс-бар опыта
- Статистика боёв: побед / поражений / винрейт
- Список убитых монстров (если публично)
- **Список выполненных заданий** (какие квесты пройдены)
- **Зелья и свитки, имеющиеся у пользователя** (инвентарь алхимии — публично видимая часть)
- Дата рождения — показывается в соответствии с выбором пользователя (`birthDateVisibility`): скрыта / только день и месяц / полностью

### 4.5 Личный кабинет (приватная версия)

Дополнительно к публичному профилю:
- Точный баланс валюты
- История транзакций (покупки, начисления от админа, награды за задания)
- Список активных/выполненных заданий
- **Имя и Фамилия** (опциональные поля) — заполняются и редактируются свободно самим пользователем напрямую (в отличие от никнейма, без запроса в админку), с переключателем видимости «показывать в публичном профиле» (по умолчанию выключено)
- Настройки: смена пароля, смена аватара, видимость даты рождения, видимость имени/фамилии, уведомления

**Смена отображаемого имени (никнейма):** при регистрации пользователь выбирает любое свободное имя без ограничений. После регистрации прямое изменение поля недоступно — вместо этого пользователь подаёт запрос через личный кабинет, который попадает в очередь на рассмотрение в админ-панели (одобрить/отклонить, с одобрения меняется `displayName`).

```
DisplayNameChangeRequest {
  id
  userId: FK -> User
  currentName: string
  requestedName: string
  reason: text, optional
  status: "pending" | "approved" | "rejected"
  reviewedBy: FK -> User, optional
  createdAt: date
  reviewedAt: date, optional
}
```

Эта же модель хорошо расширяется под другие виды запросов на изменение (например, запрос на смену школы, если решите не давать школу назначать только мастеру напрямую) — можно сделать `type` полем и переиспользовать структуру для нескольких видов заявок пользователя.

### 4.6 Школы фехтования

Вы прислали «Кодекс цеха» — устав клуба, из которого видно, что школы это не просто лор-карточки, а реальные игромеханические профили: оружие, ХП, урон, слоты Знаков, порог интоксикации и особые способности. Ниже — школы по документу:

| Школа | Оружие | ХП | Урон | Слоты знаков | Порог интоксикации | Особенности |
|---|---|---|---|---|---|---|
| 🐺 Волка | Полуторный меч | 10 | 1 | 3 | 100% | Может использовать 1 эликсир дважды |
| 🦂 Мантикоры | Стафф | 10 | 1 | 2 | 130% | — |
| 🐻 Медведя | Цвайхандер | 15 | 1 | 2 | 100% | — |
| 🐱 Кота | Парные короткие одноручные мечи | 8 | 2 | 3 | 100% | Попадание в торс наносит на 1 ед. больше урона |
| 🐍 Змеи | Катана | 10 | 1 | 3 | 100% | Использование ядов; выбор одной из 2 веток развития (мастерство ядов / использование фамильяра) |
| 🦅 Грифона | Баклер + деревянный меч | 10 | 0 | 4 | 100% | Может восстанавливать использование Знаков; урон оружия эликсирами не увеличивается |
| 🦊 Лисы | Лук + одноручный меч | 8 | лук 2–3 (растёт с дистанцией), меч 1 | 2 | 100% | Колчан по умолчанию на 3 стрелы; урон лука не увеличивается эликсирами; можно покупать стрелы с эффектами |
| 🦡 Россомахи | Два топора | — | — | — | — | **В разработке**, параметры пока не заданы (оставляем как есть, без сроков) |

Важное уточнение: сайт **не проводит и не рассчитывает бои** — все эти характеристики выводятся на сайте исключительно как справочная информация для живых РПГ-боёв (реальной фехтовальной отыгровки в клубе), а не как данные для игрового движка. Это заметно упрощает модель — не нужен отдельный «боевой лист» с расчётом текущего ХП, списанием интоксикации и т.д., достаточно карточки школы как справочника:

```
School {
  id
  name (например, «Школа Волка»)
  description
  iconUrl / emblemUrl
  weaponType: string                    // например, "Полуторный меч"; для школ с несколькими типами оружия (Лиса) — просто перечисляется текстом
  baseHp: int, optional
  baseDamage: string                    // текстовое поле, а не число — у Лисы, например, "лук 2–3 (по дистанции), меч 1"
  signSlots: int, optional
  intoxicationThreshold: int, optional  // % порога интоксикации
  specialAbilities: text                // особенности школы (см. таблицу выше), свободный текст
  status: "active" | "in_development"
}
```

Присвоение школы пользователю — **назначает админ/мастер** (не свободный выбор при регистрации), обычно по итогам какого-то испытания/собеседования с мастером. У нового пользователя школа не заполнена до этого момента.

Знаки, Эликсиры и Мутагены, упомянутые в Кодексе как часть ролевой боевой системы, на сайте не нужно моделировать отдельной боевой сущностью — они уже покрываются справочником эффектов зелий/свитков (раздел 4.8) там, где это нужно для магазина, а как боевые правила остаются на стороне живой игры.

Админ-панель: CRUD по школам (все параметры из таблицы выше, включая «в разработке»/«активна»), назначение школы пользователю мастером/админом.

### 4.7 Бестиарий

Две разные сущности, которые не стоит путать:
- **Бестиарий** — справочник видов монстров (например, «Утопец», «Накер», «Грифон-мутант»): описание, категория, уровень опасности, лор-текст, изображение. Это статичная энциклопедия.
- **Убитые монстры** — журнал охот: запись вида «пользователь X убил монстра вида Y (из бестиария) числа such-and-such», обычно привязана к конкретному бою или отдельной охоте.

```
Bestiary {
  id
  name
  category (например: низший вид / реликт / гибрид / проклятье)
  dangerLevel: int или enum (низкая/средняя/высокая/смертельная)
  description
  imageUrl
}

MonsterKill {
  id
  userId: FK -> User
  bestiaryId: FK -> Bestiary
  battleId: FK -> Battle, optional (если убийство произошло в рамках боя/охоты)
  date
  notes: text, optional
  recordedBy: FK -> User        // админ/судья, зафиксировавший убийство — запись создаётся только им, без заявок от пользователей
  rewardGranted: bool
  rewardGrantedBy: FK -> User, optional  // кто начислил награду (тоже вручную)
  rewardExperience: int, optional
  rewardCurrency: int, optional
}
```

Записи об убийстве монстра создаются **только админом/судьёй** по итогам боя/охоты — самозаявление пользователем с последующей модерацией не предусмотрено. То же касается наград: начисление опыта и кронов — вручную, тем же лицом, что зафиксировало убийство, или другим уполномоченным.

Админ-панель: CRUD по видам бестиария; форма добавления записи об убийстве (выбор пользователя, вида монстра, боя, начисление награды) — доступна ролям с правом `canRecordKills`.

### 4.8 Лавка алхимика (в разработке)

Логически — часть общего магазина, но со своей категорией и своей игровой механикой: зелья и свитки имеют реальные эффекты, а не просто косметику. Вы прислали документ «Своё Дело» с полным перечнем эликсиров и свитков — ниже модель уже учитывает их реальную структуру, а не гипотетическую.

```
ShopItem {
  id
  name
  category: "general" | "potion" | "scroll" | ...
  price: int                        // цена в кронах
  description
  imageUrl
  stock: int, optional               // ограничение количества, если нужно
  isActive: bool
  minRankId: FK -> Rank, optional    // минимальный ранг для использования (для эликсиров — обязательно)
  toxicity: int, optional            // % токсичности/интоксикации разового применения (только для эликсиров)
  effects: [ItemEffect]              // список эффектов, см. ниже
}

ItemEffect {
  id
  type: "hp" | "damage" | "sign_slot" | "sign_power" | "poison_resist" |
        "aksiy_resist" | "regen" | "task_add" | "task_repeat" | "task_summon" |
        "task_refresh" | "task_retry" | ... // расширяемый справочник типов
  value: number, optional            // числовое значение эффекта (например, +2 макс. ХП)
  duration: "instant" | "temporary" | "permanent"
  durationValue: number, optional    // если temporary — на сколько (тактов/боёв)
}
```

Ключевой момент: тип эффекта (`type`) — это справочник, редактируемый в админке, а не жёстко зашитый список.

**Эликсиры** — создаются Мастером Алхимиком клуба (по документу — за рецепт, кроны и трофеи), большинство одноразовые «навсегда» (крафтятся один раз). Каждый эликсир привязан к минимальному рангу и имеет токсичность. Примеры из присланного документа (заносятся как реальные товары, не абстрактный пример):

| Название | Мин. ранг | Токсичность | Эффект |
|---|---|---|---|
| Грач | Серебряный кандидат | 30% | +1 к урону клинка |
| Новолуние | Серебряный кандидат | 30% | +2 к макс. ХП |
| Чаша Вильгефорца | Серебряный кандидат | 30% | +1 слот для использования знаков |
| Филин | Серебряный кандидат | 30% | +1 сила знаков |
| Ласточка | Серебряный кандидат | 0% за первую, 30% за каждую следующую | Следующие 5 тактов боя восстанавливают 1 хит, суммируется |
| Иволга 1 ур. | Серебряный кандидат | 0% за первую, 30% за каждую следующую | Игнорирует/снимает 1 яд |
| Иволга 2 ур. | Признанный Ведьмак | 45% | Игнорирует/снимает 2 яда |
| Волк 1 ур. | Младший Ведьмак | 45% | Попадание в корпус — на 1 ед. урона больше |
| Волк 2 ур. | Признанный Ведьмак | 45% | Попадание в корпус — на 2 ед. урона больше |
| Гром 1 ур. | Младший Ведьмак | 45% | Урон клинка +2, входящий урон +1 |
| Гром 2 ур. | Признанный Ведьмак | 60% | Урон клинка +3, входящий урон +1 |
| Ива 1 ур. | Младший Ведьмак | 45% | Игнорирует 1 Аксий |
| Ива 2 ур. | Признанный Ведьмак | 60% | Игнорирует 2 Аксия |
| Кряква | Младший Ведьмак | 30% | Спец-эффект: -1 урон клинка и -1 слот знака, но +1 хп каждые 10 тактов; особый эффект при 0 слотов/уроне 1 |
| Вирга 1 ур. | Младший Ведьмак | 45% | Игнорирует 1 знак на базе Игни или 1 яд |
| Вирга 2 ур. | Признанный Ведьмак | 60% | Игнорирует 2 знака на базе Игни или 2 яда |

Как и с параметрами школ (4.6) — это справочные данные для живой отыгровки боя, сайт их не рассчитывает автоматически. На сайте эликсир — товар с описанием, минимальным рангом и токсичностью, доступный для просмотра/покупки; участник и судья сверяются с текстом эффекта во время реального боя.

**Свитки** — физический токен квеста в реальности клуба: квест считается взятым, когда участник берёт свиток в руки, и выполненным — только когда свиток возвращён мастеру (в конце тренировки свиток обязательно возвращается на доску). Это напрямую связано с моделью заданий (`TaskTemplate.maxSlots`, см. 4.12) — количество одновременно доступных копий задания физически равно количеству свитков этого квеста в обороте. Эпические квесты выполняются только один раз.

Реальный список свитков из документа:

| Свиток | Эффект | Цена |
|---|---|---|
| Свиток дополнения | Позволяет выполнить ещё 1 квест на тренировке | 100 крон |
| Свиток повтора | Позволяет повторно выполнить любой квест | 200 крон |
| Свиток вызова | Позволяет призвать любой квест, даже если его нет на доске | 50 крон |
| Свиток обновления | Заменяет квест в руке на случайный, ещё не выполненный | 10 крон |
| Свиток попытки | Позволяет повторно попытаться выполнить провальный квест (кроме отдельных долгих квестов вроде «Тишина») | 50 крон |

На старте: реализовать вывод товаров с фильтром по категории (обычные / зелья / свитки), с полями минимального ранга и токсичности у эликсиров, плюс отображение эффектов на карточке товара. Список наверняка будет пополняться (по вашим словам) — модель это уже поддерживает без изменений в коде.

Админ-панель: CRUD по товарам (включая зельям/свиткам, минимальный ранг, токсичность), CRUD по типам эффектов (`effect type`), назначение одного или нескольких эффектов на товар.

### 4.9 Ведьмачьи знаки (справочно)

Отдельная механика из документа, тоже чисто справочная (для живого боя, не для расчёта сайтом): участник открывает возможность использовать Знаки, достигнув 25 уровня и пройдя квесты «Испытание травами» и «Поиск святилищ» — после этого доступны 3 базовых знака (Игни, Аксий, Квен), а по квесту «Поиск святилищ 2» (доступен с ранга «Серебряный кандидат») — ещё 3 продвинутых.

Для сайта это можно оформить простой справочной страницей/таблицей (название знака, описание эффекта, условие получения) без какой-либо игровой логики — как ещё один раздел энциклопедии, наравне с бестиарием и школами. Полный список продвинутых знаков вы уточните позже, как и с эффектами зелий.

### 4.11 Уровни, опыт и ранги цеха

Числовой уровень и опыт (кроны — внутренняя валюта, тоже подтверждено Кодексом цеха):
- Пока всё начисляется **вручную через админку** — опыт, уровень и кроны не считаются автоматически за победы/задания на данном этапе. Позже это можно автоматизировать, но на старте — полностью ручное управление.
- Кроны — заработок только через квесты/активности клуба; **покупка кронов за реальные деньги запрещена регламентом клуба** — это стоит явно заблокировать и на уровне сайта (не давать возможности пополнить баланс кронов оплатой, только начисление админом/мастером).

Кроме числового уровня, есть система **рангов цеха** — именной статус со своими требованиями и наградами. По Кодексу цеха, официальный список рангов:

Рекрут → Ученик → Бронзовый Кандидат → Серебряный Кандидат → Золотой Кандидат → Младший ведьмак → Признанный Ведьмак → **Мастер Ведьмак**

Восьмой ранг («Мастер Ведьмак») официально существует по документу, но требования и награды для него не зафиксированы — остаётся на сайте с пометкой «уточняется» (в документе указано, что актуальные требования к повышению ранга публикуются в телеграм-канале клуба). Требования и награды для остальных рангов ниже — подтверждены присланным документом «Своё Дело» дословно, совпадают с расшифровкой из прошлого раунда:

| Ранг | Требования | Награда |
|---|---|---|
| 🛡 Рекрут цеха | 0 уровень (присваивается автоматически при регистрации) | Кулон рекрута цеха |
| ⚔️ Ученик цеха | 5 уровень; 3 победы над членами цеха ранга «Ученик» и выше | Допуск к выполнению более сложных линеек цеха, место на доске почёта |
| 🏅 Бронзовый кандидат цеха | 15 уровень; 5 побед над членами цеха ранга «Бронзовый кандидат» и выше | Браслет бронзового кандидата, место на доске почёта бронзовых кандидатов |
| 🏅 Серебряный кандидат цеха | 25 уровень; 10 побед над членами ранга «Бронзовый кандидат» и выше; 3 RPG-победы; 3 подмастерья + 2 мастера; испытание травами; поиск святилищ; 3 трофея с убитых монстров | Браслет серебряного кандидата, скидка 10%, место на доске почёта серебряных кандидатов |

| 🐺 Младший ведьмак школы | 50 уровень; испытание медальоном | Медальон школы, знаки школы, скидка 30%, место на доске почёта младших ведьмаков |
| 🐺 Признанный Ведьмак | 70 уровень; 21 победа; 11 RPG-побед; все подмастерья, все мастера; 6 квестовых линий; 1 отвар; 1 ветка мутаций | Личный клинок, слоты брони персонажа, личный алхимик, скидка 50%, скидка 50% на крафт, место на доске почёта |

Модель данных для этого:

```
Rank {
  id
  name (например, «Ученик цеха»)
  icon / emoji
  order: int                       // порядок в иерархии, для сортировки и проверки "и выше"
  requirements: [RankRequirement]  // гибкий список условий
  rewards: [RankReward]            // гибкий список наград
}

RankRequirement {
  type: "level" | "wins_vs_rank" | "rpg_wins" | "journeyman_count" | "master_count" |
        "trial" | "monster_trophies" | "quest_lines" | "custom"
  value: number, optional
  targetRankId: FK -> Rank, optional   // для условий вида "N побед над членами ранга X и выше"

}
```

Типы требований/наград сделаны расширяемым списком, а не жёстким набором полей — раз ранги уже сейчас разнородные (трофеи, испытания, РПГ-победы), новые почти наверняка принесут новые виды условий и наград. Так как требования к рангам могут меняться (по документу — публикуются в телеграм-канале), список `requirements`/`rewards` каждого ранга должен свободно редактироваться в админке без деплоя кода.

**Присвоение ранга — по заявке пользователя с ручной проверкой мастером/админом**, не автоматически:

```
RankUpRequest {
  id
  userId: FK -> User
  fromRankId: FK -> Rank
  toRankId: FK -> Rank
  status: "pending" | "approved" | "rejected"
  reviewedBy: FK -> User, optional
  comment: text, optional
  createdAt: date
  reviewedAt: date, optional
}
```

Пользователь подаёт заявку на повышение ранга (например, из личного кабинета — «Подать заявку на ранг Ученик»), заявка попадает в очередь, мастер/админ вручную проверяет выполнение условий (в том числе нецифровых вроде «испытание травами») и одобряет/отклоняет.

Админ-панель: CRUD по рангам (название, иконка, порядок, требования, награды), очередь заявок на повышение ранга (`RankUpRequest`) с ручным подтверждением.

### 4.12 Задания

Нужно различать два числа, которые вы упомянули:
- **Сколько раз задание выполнено** (счётчик выполнений, растёт с каждым завершением)
- **Сколько одинаковых копий задания сейчас доступно** (лимит — например, задание «Победить 3 утопцев» может быть доступно только 5 пользователям одновременно, дальше слоты закрываются)

```
TaskTemplate {
  id
  title
  description
  reward: { experience: int, currency: int }
  maxSlots: int, optional     // сколько одинаковых копий доступно одновременно (null = без лимита)
  isRepeatable: bool          // может ли один пользователь брать его повторно
  isActive: bool
}

TaskAssignment {
  id
  taskTemplateId: FK -> TaskTemplate
  userId: FK -> User
  status: "in_progress" | "completed" | "failed" | "cancelled"
  assignedAt: date
  completedAt: date, optional
}
```

- Счётчик выполнений = COUNT(TaskAssignment где status = completed) по конкретному TaskTemplate
- Текущая доступность = maxSlots − COUNT(TaskAssignment где status = in_progress) по конкретному TaskTemplate
- Если isRepeatable = false, один и тот же пользователь не может второй раз взять то же задание (проверка при выдаче)

Админ-панель: CRUD по TaskTemplate (название, описание, награда, лимит копий, повторяемость), просмотр статистики выполнений по каждому заданию, ручное управление статусами TaskAssignment (например, принудительно закрыть/отменить).

- Последние начисления валюты

```
ActivityLogEntry {

}
```

Технически проще всего реализовать через Django-сигналы (`post_save` на ключевых моделях) — при создании/изменении важных объектов пишется запись в `ActivityLogEntry`, а дашборд просто выводит последние N записей с фильтрами по типу. Дни рождения — отдельная выборка (не событие, а вычисляемый список «у кого ДР в ближайшие 7 дней»), не через ActivityLogEntry.

### 4.14 Дуэльный кодекс и модель боя

Из Кодекса цеха: в ранговых и квестовых боях обязательны Главный и Боковой судьи; в тренировочных — по усмотрению мастеров. Бои делятся на **ТС** (Тренировочная Схватка — счёт на очки) и **РС** (Ролевая Схватка — до условной «смерти»/поражения аватара). Отдельно есть Турниры, которые могут состоять из боёв обоих типов.

```
Battle {
  id
  type: "ТС" | "РС"
  fighter1Id: FK -> User
  fighter2Id: FK -> User
  winnerId: FK -> User, optional        // может отсутствовать (ничья/дубль)
  mainJudgeId: FK -> User               // Главный судья — обязателен для ранговых/квестовых боёв
  sideJudgeId: FK -> User, optional     // Боковой судья
  tournamentId: FK -> Tournament, optional
  isRanked: bool                        // ранговый/квестовый (обязателен судья) или тренировочный
  date
  notes: text, optional
  recordedBy: FK -> User                // запись создаёт только судья/админ — без самозаявления участников
}
```

Подтверждено: результаты боёв фиксируются **только судьёй/админом**, участники сами запись не создают и не подтверждают.

### 4.15 Фестивали

```
Festival {
  id
  title
  description
  date / dateRange
  photos: [ImageUrl]           // галерея фото фестиваля
  blogPostIds: [FK -> BlogPost] // связанные посты блога
}
```

Связь двусторонняя: на странице фестиваля — ссылки на посты блога о нём, на странице поста блога — ссылка обратно на фестиваль (если пост создаётся «в привязке» к конкретному фестивалю). Проще всего реализовать как обычную FK-связь `BlogPost.festivalId`, а на странице фестиваля выводить все посты с этим `festivalId` — тогда обратная ссылка не требует отдельного поля, просто выводится автоматически.

### 4.16 Соц-сети клуба, мастеров, оружейни

Простой редактируемый список ссылок, без сложной модели — единый справочник, который выводится блоками в подвале сайта / на странице контактов:

```
SocialLink {
  id
  ownerType: "club" | "master" | "armory"
  ownerId: FK -> User, optional    // заполняется, если ownerType = "master" (ссылка на конкретного мастера/школу)
  platform: string                  // "Telegram", "VK", "Instagram" и т.д.
  url
  label: string, optional           // подпись, если нужна
}
```

Админ-панель: CRUD по ссылкам, с фильтром по типу владельца.

### 4.17 Система взысканий

По Кодексу цеха у ГК/ДГК (и, по вашему решению, у любых ролей с соответствующим правом) есть возможность накладывать взыскания на участников: Замечание, Боевое замечание, Предупреждение, Временное отстранение от ранговых/квестовых/турнирных боёв, Временный бан, Обнуление персонажа, Бессрочный бан. По регламенту три замечания конвертируются в одно предупреждение, три боевых замечания за один бой — в одно замечание, а сами замечания/предупреждения сгорают без повторных нарушений (замечание — через 1 месяц, предупреждение — через 3 месяца).

```
Penalty {
  id
  userId: FK -> User
  type: "remark" | "battle_remark" | "warning" | "battle_suspension" |
        "temp_ban" | "character_reset" | "permanent_ban"
  reason: text
  issuedBy: FK -> User            // роль с правом canIssuePenalties
  relatedBattleId: FK -> Battle, optional   // если взыскание вынесено по итогам конкретного боя
  issuedAt: date
  expiresAt: date, optional       // для авто-сгорания замечаний/предупреждений
  status: "active" | "expired" | "cancelled"
  cancelledBy: FK -> User, optional   // отменить взыскание может только Глава Клуба, по регламенту
  cancelReason: text, optional
}
```

Функциональность на сайте:
- **«Вынести взыскание»** — кнопка/форма, доступная ролям с правом `canIssuePenalties` (по регламенту это как минимум ГК и ДГК, но право можно выдать и другим ролям, например Мастеру школы — вы это настраиваете в Django admin)
- **История взысканий** — видна самому пользователю в личном кабинете и ролям с правом `canViewPenalties`/`canIssuePenalties` на странице пользователя в админке; публично не отображается
- Автоматическое сгорание (замечание/предупреждение) — фоновая задача, переводящая `status` в `expired` по истечении `expiresAt`. Автоматическая конвертация «3 замечания → 1 предупреждение» и «3 боевых замечания → 1 замечание» на данном этапе **не реализуется** — подсчёт и решение о переводе в следующую категорию взыскания остаётся на усмотрение того, кто выносит взыскание (вручную, глядя на историю пользователя)
- Отмена взыскания — отдельное действие с указанием причины. По регламенту клуба это право только у Главы Клуба (`canCancelPenalties`), но на сайте Админ (техническая роль) имеет право на все действия без ограничений — в том числе отмену взысканий, вне зависимости от того, кто выступает Главой Клуба в реальности

Админ-панель: список всех взысканий с фильтрами по пользователю/типу/статусу, форма выдачи нового взыскания, кнопка отмены (для уполномоченной роли).

## 6. Открытые вопросы

### Решено в этом раунде

Для истории — вот что уже закрыто вашими ответами и больше не требует решения:
- Модерация аватаров — отложена
- Результаты боёв фиксирует только судья/админ
- Валюта начисляется только вручную через админку
- Публичность даты рождения, имени/фамилии — выбор пользователя
- Параметры школ — справочные, для живых РПГ-боёв (сайт бои не рассчитывает)
- Школу назначает админ/мастер
- Зелья влияют на живые РПГ-бои, но не через движок сайта
- Записи об убийстве монстра создаёт только админ/судья
- Абонементы — витрина за реальные деньги (+опционально в кронах), без оплаты на сайте
- Ранг присваивается по заявке пользователя с ручной проверкой
- Ранг «Мастер Ведьмак» и школа «Россомаха» — остаются на сайте с пометкой «в разработке» / «уточняется», без блокирующих требований
- Требуется система взысканий (история + возможность «вынести взыскание» у уполномоченных ролей) — добавлена в раздел 4.17
- Email-верификация не обязательна для регистрации/восстановления пароля, но **обязательна для загрузки собственного аватара**
- Право отмены взыскания — у Админа сайта есть все права по умолчанию (независимо от офлайн-иерархии ГК/ДГК)
- Реальный список эликсиров (15 шт.), свитков (5 шт.), билетов-абонементов (10 шт.) и цен на разовые активности — получен из документа «Своё Дело», занесён в разделы 4.8 и 4.10 как реальные данные, а не пример
- Цена билета «Командира» — 1490 BYN (включает подарок: личный клинок выбранной школы), уточнено и занесено в таблицу
- Автоматическая конвертация взысканий — не требуется (пока что); в модели `Penalty` (4.17) достаточно ручного учёта, без логики авто-суммирования замечаний в предупреждение
